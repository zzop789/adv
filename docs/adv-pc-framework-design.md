# ADV PC 框架设计基线

版本：v1.5

确定日期：2026-10-02

当前状态：阶段 1–3 及制作 API A–D 已实现，包含动态内容应用、统一动效和本地可视化流程编辑器。阶段 4 和阶段 5 待开发。当前已有两个独立 Windows x64 便携包。

本文固定当前项目的产品范围、技术选型、目录、模块职责和开发顺序，作为后续实现的统一依据。目标是制作一个可以批量生产独立 ADV 游戏的框架，重点支持每款作品大幅更换 UI 和播放素材。

## 产品目标

当前只开发 Windows PC 版本。程序、剧情和素材随作品交付，游玩及存档在本地完成，不依赖业务服务器。

每款成品由以下部分组成：

> 固定版本的共享内核 + 作品专属 UI + 剧情配置 + 本地素材 = 一款独立 ADV 游戏

主要内容形式是互动影游：视频播放、分支选择，以及后续逐步加入的立绘文字、QTE 和热点调查。不开发战斗系统。

批量生产的目标是：制作下一部作品时，主要修改它自己的 UI、剧情与素材，共享内核基本不变。新增真正的玩法规则时，可以扩展内核能力，但普通界面变化不应要求修改剧情执行逻辑。

## 当前范围

| 范围 | 决定 |
| --- | --- |
| 运行平台 | Windows PC |
| 运行方式 | 本地离线 |
| 产品交付 | 每款作品独立打包，独立名称、图标与存档空间 |
| 主要可变部分 | UI 结构、布局、动效、界面流程，以及视频和其他素材 |
| 共用部分 | 剧情执行、播放控制、互动规则、存档基础能力和构建流程 |
| 后续平台 | 手机与网页留到后续开发，当前不实现多端适配层 |
| 当前不建设 | 作品平台、统一启动器、服务器、账号、云存档、在线热更新和万能 UI/视频剪辑编辑器 |

先把一个 PC 成品的生产流程跑通，再增加框架能力。目录中规划了工具与测试位置，不表示首期需要建设完整工具平台。

## 技术选型

采用 Electron、TypeScript 和 React。选择依据是当前业务以视频和可大幅变化的 UI 为主，作品可以复用组件，也可以替换整套界面实现。

| 技术 | 用途 | 引入阶段 |
| --- | --- | --- |
| Electron | 桌面窗口、应用生命周期、本地能力和 PC 交付 | 阶段 1 |
| TypeScript | 共享逻辑、配置类型和模块接口 | 阶段 1 |
| React 和 CSS | 基础界面与作品专属 UI | 阶段 1 |
| Vite | 前端开发与构建 | 阶段 1 |
| HTMLVideo | 本地视频播放底层，由播放控制器封装 | 阶段 1 |
| Zod | 校验作品配置、剧情和素材清单的结构 | 随对应数据格式引入 |
| rcedit | 制作阶段写入 Windows EXE 图标与产品信息 | 阶段 3，仅构建依赖 |
| FFmpeg 和 ffprobe | 制作阶段转码、检查视频信息 | 有素材处理需求时引入 |

具体依赖版本在搭建工程时核验并通过锁文件固定。FFmpeg 不作为玩家运行游戏的外部安装前提。当前不引入 Ink、Yarn、HLS 或插件系统作为必需依赖。节点编辑器使用 React + SVG，动效使用 Web Animations，不增加第三方运行依赖。

## 模块职责

| 模块 | 负责 | 不承担 |
| --- | --- | --- |
| desktop | 窗口、应用生命周期、本地文件访问、存档文件读写 | 剧情分支判断 |
| authoring | 编辑剧情草稿、撤销重做、制作校验和版本冲突检查 | 直接修改玩家运行中的会话 |
| editor | 节点图、字段表单、历史和草稿预览 | 绕过校验写文件、进入玩家发布包 |
| runtime | 剧情位置、变量、选择结果、合法状态转换、暂停状态和存档数据 | 具体按钮、布局、文件路径和视频解码 |
| presentation | 按指令执行视频等演出，报告完成、进度或失败 | 自行决定剧情去向 |
| ui-base | 提供可复用的按钮、面板等基础组件 | 强制所有作品采用同一套界面 |
| 作品 UI | 显示状态、组织界面、管理菜单导航、提交玩家操作 | 直接修改剧情变量或自行提交剧情跳转 |
| 作品配置与素材 | 提供作品信息、剧情、资源映射与内容 | 放置共享框架逻辑 |
| tools | 检查内容并生成作品发布包 | 承担玩家运行时的在线服务 |

Electron 的本地能力通过明确接口提供给界面。剧情内核不依赖 Electron 或具体 UI 组件，以便单独验证其行为。

## UI 与剧情的接口

内核输出当前可显示的状态，UI 提交操作意图。方法名及完整数据结构在实现时确定，以下固定的是职责和语义。

| 方向 | 数据或操作 |
| --- | --- |
| 内核到 UI | 当前剧情阶段、可选项、允许的操作、播放及加载状态、错误信息 |
| UI 到内核 | 开始、继续、选择选项、暂停、恢复、重新开始 |
| 后续扩展 | 对话内容、QTE 状态、调查热点、存档和读档 |

同一个选择可以显示成文字按钮、人物卡片或聊天气泡，最终都提交稳定的选项 ID 和当前访问代次，例如 `choose("tell_the_truth", story.visitId)`。界面变化不改变选项的剧情含义。

一次选择的执行顺序为：

```text
UI 提交选项 ID
    → runtime 检查当前状态并接受选择
    → runtime 切换剧情节点
    → presentation 加载对应素材并播放
    → presentation 报告完成或失败
    → runtime 决定后续行为
```

UI 支持三个层次的替换：颜色、字体和图片通过主题素材调整；位置与排列通过布局调整；界面结构和流程通过替换作品 UI 代码实现。不把所有变化强行表达为配置，不在首期开发万能 UI 编辑器。

视频播放会话独立于 UI 生命周期。打开菜单、重建界面或修改布局，不应重新进入剧情节点或让视频从头开始。UI 可以决定视频显示区域，播放状态由会话和播放控制器管理。

当前作品入口导出 `{ Layout, screens }` 注册表。Layout 接收作品信息、播放状态、播放操作、视频宿主引用和播放/剧情/弹窗插槽；每个 Screen 只接收独立数据与操作回调。通用控件位于 `ui-base`，界面管理器提供 `open/show/close` 等按名称调用入口。组件可单独使用，也可交给 UIHost 管理；详细契约见 [UI 架构与调用示例](ui-architecture.md)。

`StorySession` 连接纯剧情执行器与视频端口，宿主持有唯一视频元素；Layout 必须持续保留这个挂载区域。`player-ui` 协调层把节点转换成界面参数，使用 `visitId` 拒绝过期选择，使用 `sourceId` 区分播放代次。控件和界面自身不推进剧情，也不持有播放器。

模态界面由协调层控制暂停与恢复，最后一个弹窗关闭时只恢复同一次节点和视频的原播放。原本未开始或已经暂停的片段不会自动播放。示例设置只复用现有音量、全屏能力，不表示阶段 4 的设置持久化与存档已经完成。

## 剧情与素材管理

阶段 2 先支持三类节点：播放视频、显示选择、结束。条件变量、复杂演出和其他互动按后续需求逐项增加，不提前设计完整脚本语言。

作品配置之间的关系如下：

| 文件 | 内容 |
| --- | --- |
| game.json | 作品 ID、名称、入口剧情及构建所需的作品信息 |
| story.json | 稳定节点 ID、节点类型、素材引用、选项 ID 和目标节点 |
| assets.json | 稳定素材 ID 对应的本地文件及必要元数据 |

剧情引用素材 ID，不直接写视频文件名、机器绝对路径或 UI 控件路径。例如剧情引用 `opening_video`，`assets.json` 决定实际播放哪个文件。

换画质或压缩版本通常只需更新素材映射。重新剪辑改变了台词、时长或镜头构图时，需要复核字幕与互动位置。视频内 QTE 等能力进入开发后，再引入语义时间标记；阶段 1 和阶段 2 不要求完整时间轴系统。

制作端提供显式动态应用：新内容完整校验后，对同一会话选择从入口开始、重播节点或保留兼容进度；失败保留原状态。用素材指纹确认视频兼容性，通过独立 API 执行动效和媒体时间触发。详见 [制作 API](authoring-api-design.md)、[动态更新](dynamic-content-api.md)、[动效](effects-api.md) 和 [编辑器教程](visual-editor-guide.md)。发布时生成新的独立作品包，当前不建设在线热更新机制。

阶段 3 固定 `game.json` 为版本 2，入口为 `entryNodeId`，构建字段为 `build.executableName`、`build.appId` 和 `build.icon`。`story.json` 与 `assets.json` 使用版本 1。视频和 ICO 图标必须在作品 `media/` 内；构建复制该目录并拒绝符号链接。文件名可包含中文和空格。

构建前同时检查节点和选项 ID 是否重复、入口和跳转是否存在、素材引用是否存在、节点是否可达，以及每个节点是否都有到达结局的路径。允许有出口的循环，不允许陷入永远无法结束的子图。

## 播放与存档规则

以下规则随对应能力实现，不表示首期一次完成。

- 剧情状态由 runtime 统一维护。重复点击不能重复提交同一个选择。
- 每次播放带有可区分的会话标识，旧视频迟到的结束或加载回调不能推动当前剧情。
- 播放失败进入错误或重试状态，不能被当作正常播放完成而跳过剧情。
- 暂停与恢复由会话协调。菜单关闭不应错误解除其他仍然生效的暂停原因。
- 不预先承诺所有设备上的视频切换零间隙，实际效果使用目标 PC 和真实素材验证。
- 存档按作品 ID 隔离，并记录内容版本、存档格式版本、剧情检查点和必要状态。
- 阶段 4 先支持节点检查点存档。读档允许重播当前短视频段，不承诺任意帧或任意 QTE 中途恢复。
- 已经提交的剧情结果在读档时不能重复执行。不兼容内容更新需要明确处理，不把旧视频秒数直接套用到新剪辑。

## 开发顺序与验收

阶段 1–3 和制作 API A–D 已完成；后续继续阶段 4。

| 阶段 | 开发内容 | 验收产物 |
| --- | --- | --- |
| 1 桌面骨架 | Electron 窗口、作品配置读取、本地素材读取与视频播放 | Windows 上可启动的演示，能在离线状态下播放本地视频 |
| 2 最小剧情闭环 | 视频、选择和结束节点，暂停与重新开始 | 视频 A → 两个选项 → 视频 B 或 C → 结束 |
| 3 验证批量生产 | 第二套作品 UI、剧情素材组织、按作品构建 | 两个 UI 和素材明显不同的独立游戏发布包，共用同一内核 |
| 制作 API A | 流程草稿编辑、校验、安全保存、显式重载预览 | 修改内容后可重新预览，错误不覆盖文件或破坏旧会话 |
| 制作 API B–C | 运行中内容应用策略、UI 和视频动效 | 内容切换、暂停、重播与旧回调有明确规则 |
| 制作 API D | 可视化流程编辑器 | 节点图、字段、连线、历史、安全保存和草稿预览 |
| 4 基础成品能力 | 标题菜单、音量、全屏、节点检查点存档 | 可退出后继续游玩的 PC 样例 |
| 5 混合 ADV 能力 | 依次加入立绘文字、视频 QTE、静态热点调查 | 覆盖目标演出和互动类型的 PC 样例 |

阶段 2 必须验证正确分支、重复点击及旧播放回调，不只验证能播放视频。

阶段 3 是框架的关键验收：第二部作品主要改动自己的 UI、剧情与素材，普通界面和内容差异不要求修改共享剧情内核。若这一点无法成立，应先调整边界，再扩展功能。

阶段 5 逐项实现并验证暂停、恢复与存档之间的关系。视频同步 QTE 使用媒体时间判断，避免视频停顿时互动计时仍继续推进。

阶段 1 已交付 Windows 窗口、作品与素材配置读取、本地视频播放器和示例作品 UI，支持暂停、重播、进度、音量与全屏。暂停和重播作为播放器基础控制提前完成；剧情节点和分支仍属于阶段 2。

阶段 2 实现了 `StoryRunner`、`StorySession` 和剧情校验。入口视频等待玩家开始，后续分支视频自动播放；选择及结局保留上一段的末帧。加载失败不推进剧情，重新载入重试当前节点。重新开始从入口播放。

阶段 3 使用《雾港》与《余光来信》验证批量生产：前者为暗色影院覆盖式选项，后者为明亮信件双栏布局，视频与图标均不同。`@work-ui` 在构建时选择目标 UI，共享剧情内核无作品名称或分支特例。

`npm run package:all` 分别生成 `FogHarbor-win32-x64` 和 `AfterglowLetter-win32-x64`。每个完整文件夹均可独立离线启动，无需开发环境；包内只有目标作品内容和运行时。名称、EXE 图标和应用数据目录隔离；当前尚无存档逻辑。发布包保留第三方许可，尚未代码签名或提供安装向导。

[制作 API](authoring-api-design.md) 已完成，接下来继续阶段 4 的标题菜单、设置持久化和节点检查点存档。现有音量和全屏属于已提前实现的基础播放能力。多轨视频时间轴、在线服务和其他平台继续后置。阶段 3 验证方法与审查修复详见 [阶段 3 Review](review-stage-3.md)。
